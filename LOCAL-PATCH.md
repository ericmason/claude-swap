# Local patch: `fix/wrong-account-and-resume-logout`

This checkout carries a local fix that is not upstream. `cswap` on this machine is installed from this branch, not from PyPI.

## What the patch fixes

Two ways `cswap` acted on the wrong account.

**Mid-session logout.** `profile_is_quiescent` in `src/claude_swap/session.py` trusted only Claude Code's own session registry. A live instance can be missing from that registry — `claude --resume` mains with no record are the observed case — so a busy profile read as idle and `_bootstrap` rewrote its keychain credentials underneath a running session. That session was logged out mid-conversation.

The fix adds `scan_env_bound_claude(session_dir)` in `src/claude_swap/process_detection.py`, which asks the OS which processes are bound to that profile through `CLAUDE_CONFIG_DIR`. Each process is read from a structured source: `/proc/<pid>/cmdline` and `/proc/<pid>/environ` on Linux, `KERN_PROCARGS2` through `sysctl` on macOS. Both hand back argv and the environment as NUL-separated records, exactly as `execve` received them, so a path with a space in it stays one argument and no amount of assignment-shaped text in an argument can be mistaken for an environment variable.

`_classify_argv_tokens` decides what counts: a `claude` main, a `main --resume`, and a node-hosted main from the npm layout all count; a shell that merely inherited the variable, a tool subprocess, a worker handed the entrypoint's path, and a `node --eval` or `node -pe` one-liner do not. Bash-tool shells outlive their parent and outnumber real mains roughly nine to one, so binding on the variable alone would pin a profile un-quiescent forever.

Interpreter options are read from a closed table, one per interpreter family, listing which options take a value and which do not. An option in neither list stops the walk and reports unknown. Guessing was the failure the table replaces: `node --inspect-port 0 /opt/bin/claude` read `0` as the script and filed a live main as idle, and no flag list stays complete on its own. A bare `-` and a `--` are not options and are handled before that rule, because `python -` runs a program from stdin and catching it as an unknown option held every profile non-quiescent for as long as one such process ran.

The node table is generated rather than transcribed. `tools/regen_node_options.py` parses `node --help` and `node --v8-options` into `src/claude_swap/_node_options.py`, and a test re-parses them at run time and fails when the shipped table and the local interpreter file an option on opposite arity sides. The option lists themselves are compared only when the local node is the same major the table was generated from, because V8 adds and drops dozens of options every major and CI runners carry whatever node their image ships. Transcribing by hand had already dropped two options and filed `--experimental-test-isolation` as taking no value when it takes one, and an option on the wrong side either swallows a main's script argument or leaves its value looking like one. V8's own type names decide arity, and `maybe_bool` is the trap in that list: an option such as `--enable-armv7` takes a value only when one is attached with `=`, so filing it with the options that swallow the next token made `node --enable-armv7 /opt/bin/claude` read as a main with no script. Against every readable process on this machine, 79 node and 6 python, the table leaves none unresolved.

An interpreter subcommand does not hide the script either: `bun run`, `deno run`, and their `exec` and `x` spellings put a word before the entrypoint, and reading that word as the script filed a live bun- or deno-hosted session as not-a-main. A relative entrypoint is resolved against the process's own working directory, read from `PROC_PIDVNODEPATHINFO` on macOS and `/proc/<pid>/cwd` on Linux, because `node cli.js` names a different file from every directory and is exactly how a main started from the package directory looks. When the working directory cannot be read, the verdict is unknown rather than not-a-main.

Once the walk has consumed an option value it cannot place the tokens after it, so no negative verdict from that point is exact. Every negative exit passes through one check that turns it into unknown, rather than each exit remembering to.

`ps` remains only as the last resort, for pids the kernel refuses and for platforms neither source covers. Everything `ps` prints is flattened and space-separated, so it cannot always tell an argument from a variable or one value from the next. Those cases report unknown rather than guessing: a repeated variable name, a value that reaches a space, a binding present in the text that did not survive the parse, or an argument the walk could not place because a consumed option value held a space. Each of the three `ps` probes can fail on its own, and a failed probe is an absent answer rather than a negative one, so a pid none of them reported is unknown too. Apple's `ps` also reports failure in the shape of an answer: it prints the kernel's short process name in parentheses, `(claude)` or `(node)`, when it cannot read the argument area, and reading that as a program name called a live session "not claude". A parenthesized name is treated as no answer at all, in argv as well as in the short-name field: `ps` wraps both, and handling only the short name left `(claude)` in argv still reading as a program called something other than claude. The one exception to the rule is a pid that no longer exists: `ps` is snapshotted once, after the pid listing, so a short-lived process can be listed and then be gone, and deferring on those wedged every profile on a busy machine.

Where the two `ps` readings disagree, the executable outranks the flattened argv, because `ps` prints the executable as a single field and it survives a path with a space in it that the flattened argv does not. An executable that names the CLI settles the pid as a main whatever argv says. One that names an interpreter leaves argv's negative too weak to settle anything, so the environment decides — and an environment naming another profile is conclusive whatever the program turned out to be, which is what keeps the machine's several dozen node processes from all deferring.

The resolved path of `claude` on PATH is looked up once and cached, and the cache is one value rather than a flag beside a value. Publishing the flag first let a second thread read "already looked" before the answer was stored, take the missing answer for "no native binary", and classify a live native main as not the CLI. Two threads reach it, the menubar refresh and the CLI, and the window is a PATH walk wide.

That is the rule the whole probe runs on: a pid is unbound only when its program and its environment were both read from a source that says where each argument ends, and neither named claude. Anything that could not be read is unknown, never unbound.

The probe fails closed. It returns `(pids, probed)`, and `profile_is_quiescent` reports idle only when `probed` is true and the list is empty. A process that could be a `claude` main and could not be read leaves this profile's liveness unknown, and re-seeding credentials on an unknown is the same mid-session logout reached by a different route. The same guard runs before backup-credential invalidation deletes a profile's credential material, and an unreadable session-registry record defers there too. A switch onto a slot whose profile could not be confirmed idle refuses for the same reason, and that one refusal `--force` overrides: it warns that the backup may be a generation a session already consumed. What `--force` never overrides is a live profile that has rotated past the backup, where activating it can only fail.

Every caller asks whether the profile is busy rather than by whom, so the scan stops at the first main it finds and the returned list is not exhaustive. Before reading a pid's full argument area, a cheap check rules it out: `proc_pidpath` on macOS, the world-readable `cmdline` on Linux. That check is a denylist, not an allowlist. It rules a process out only when it positively recognizes the executable as something that cannot host a Claude main: a shell, a coreutil, a packaged tool, or a file under a directory macOS seals, whose contents are cryptographically verified and replaced only by a system update. Everything else falls through to the full argv and environment read, so a renamed or unpackaged executable such as `/opt/tools/assistant` is read rather than dismissed. Location is weaker than that for anywhere else. `/Library` and the inside of an app, framework, or system-extension bundle are writable by whoever installed the software there, so `/Library/Acme/assistant` running `claude --resume` is a real shape; those are ruled out only once argv has been read and says the process is not a main. An allowlist had the opposite failure and hid six of the eight real sessions running on this machine, because the native installer runs a version-named file such as `~/.local/share/claude/versions/2.1.269` behind a `~/.local/bin/claude` symlink. A claude-shaped name still wins over location: a version-named file, a path with a `claude` component, an interpreter, and the resolved target of `claude` on PATH are never ruled out by where they live. Interpreters are matched without regard to case or spelling, because a framework build runs as `Python` with a capital P from inside `Python.app/Contents/MacOS` and Debian spells node `nodejs`. On this machine the check settles 1268 of 1520 pids, and a full scan that matches nothing takes 0.51s.

Process ownership is the other thing the probe may rule out on. A `claude` bound to a profile this tool manages runs as the user running this tool, so a process owned by someone else is not the session whose credentials are about to be rewritten. That matters because another user's environment is exactly what neither `ps` nor `/proc` will show: without this rule the sixteen root-owned daemons on this machine, from `nessusd` to `telegraf` to the system extensions under `/Library`, answered unknown permanently and no profile was ever quiescent. Ownership is the last reading, never the first. A process whose argv and environment were both read and name a main is a main whoever owns it, and one that was read and names something else is unbound on that reading alone; the owner is consulted only where nothing could be read at all. Where nothing could be read, another uid's process is ruled out whatever its argv looked like, claude-shaped included: the profile directory lives under this user's home and its credentials are this user's keychain and file entries, so a claude running as somebody else is that user's session rather than this one's. Exempting a claude-shaped argv meant a root-owned or other-user `claude` answered unknown for good, which on a shared Linux box left every idle profile unswitchable and gave the user nothing to exit that would clear it. An owner that cannot be read still rules nothing out. The comparison is against the effective uid, because that is what macOS `ps` reports. On Linux a `/proc/<pid>` entry that has disappeared means the process exited, which is a settled answer rather than an unreadable one.

Windows is the one carve-out. There is no cheap environment read there, so `scan_env_bound_claude` reports "probed, nothing bound" and Windows keeps the registry-only behavior that shipped before this probe existed: an unregistered `claude --resume` on Windows can still have its credentials rewritten underneath it. Failing closed instead would leave every Windows profile permanently un-re-seedable, which is worse. This fork runs on macOS.

**Stale config, wrong active slot.** The active account came from `~/.claude.json`, which goes stale the moment you log in with Claude Code directly — and that is the documented recovery for a slot whose refresh token died. An identity oracle in `src/claude_swap/switcher.py` (`_resolve_active_slot`, `_active_slot_and_identity`, `_resolve_live_identity`, `_prefetch_live_identity`, `_slot_holding_identity`) resolves the active slot from the live credential instead. The cache is keyed on the credential fingerprint, invalidated when account metadata changes, and the verdict is bound to the credential that produced it, so a cached answer cannot outlive its input. Only an identity complete enough to place a slot is cached: a uuid-only response cannot place slots that store no uuid, and remembering it would replay that unusable answer for the life of the credential instead of asking again.

## Install

```
uv tool install --force --from git+https://github.com/ericmason/claude-swap.git@fix/wrong-account-and-resume-logout claude-swap
```

This puts `cswap` and `claude-swap` on PATH at `~/.local/bin/`.

## Upgrade caveat

`cswap upgrade` runs `uv tool upgrade claude-swap`, and uv resolves that against whatever the install receipt records. After the command above, `~/.local/share/uv/tools/claude-swap/uv-receipt.toml` records the git branch rather than the PyPI package, so `cswap upgrade` cannot pull a PyPI release over this patch. It reports "Nothing to upgrade" and leaves the patched code in place.

The cost is that `cswap upgrade` can no longer bring in upstream releases at all. The update notifier still checks PyPI, so once upstream publishes a version above 0.26.0, `cswap` will say a newer version is available and `cswap upgrade` will do nothing about it. To take a new upstream release, rebase this branch onto the new tag, push it, and re-run the install command above.

To go back to stock and lose the patch, run `uv tool install --force claude-swap`.
